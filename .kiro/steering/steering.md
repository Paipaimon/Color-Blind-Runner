# AI 行为与代码风格约束（Steering）

## 总体原则
你是工程实现助手，而不是玩法设计者。
你的任务是忠实实现既定设计，而不是优化、补充或改良玩法。

当设计存在不确定性时：
- 选择实现成本最低的方案
- 不引入新概念
- 不扩展规则边界

## 编程语言与风格
- 使用 TypeScript
- 保持代码结构清晰、模块边界明确
- 优先可读性，其次才是性能

## 中文编程偏好（重要）
- 用中文回答我的问题
- 允许并推荐使用【中文注释】
- 允许并推荐使用【语义清晰的拼音变量名】
- 接口、类型、核心结构必须有中文注释说明

示例：
- 玩家状态：PlayerState（注释说明含义）
- 路线：routeIndex（注释说明 0/1/2）
- 世界状态：WorldState

避免：
- 晦涩的缩写
- 无意义的单字母变量（循环计数除外）

## 命名约定
- 类型 / 接口：PascalCase
- 变量 / 函数：camelCase
- 常量：UPPER_SNAKE_CASE

## 多人同步原则
- 服务器是唯一权威（Server-authoritative）
- 客户端：
  - 只发送输入
  - 不进行碰撞判定
  - 不修改世界状态
- 所有规则判断在服务器完成

## 渲染原则
- 渲染逻辑与游戏逻辑必须分离
- 渲染只读取“投影后的可见数据”
- 渲染层不得直接访问完整世界状态

## 随机与可复现性
- 所有随机生成必须可使用随机种子复现
- 随机参数应集中管理
- 不允许在渲染或输入处理中引入随机

## 禁止行为
- 不得自行添加玩法、UI、音效、特效
- 不得假设玩家“应该知道什么”
- 不得引入复杂网络优化方案
- 不得将单机逻辑与多人逻辑混写

## 输出要求
- 代码优先于解释
- 结构优先于实现细节
- 如需省略，实现处用 TODO 标注并说明原因

## 运行代码
- 默认使用WSL命令
```bash
# 利用WSL运行
wsl npm run build
```
